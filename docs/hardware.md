## 3. GPIO 外部上拉扫描（实测）

方法：配置为输入 + 内部下拉，仍读到 HIGH 说明存在外部上拉。

| GPIO | 上拉 | 推断归属 |
|---|---|---|
| 4 | HIGH | 相机 SCCB（I2C 上拉） |
| 5 | HIGH | 相机 SCCB（I2C 上拉） |
| 6 | HIGH | 相机 VSYNC |
| 11 | HIGH | 相机 Y2 |
| 17 | HIGH | 相机 Y8 |
| 19 | HIGH | TFT SCL（用户实测，现已不使用） |
| 20 | HIGH | TFT SDA（用户实测，现已不使用） |
| 21 | HIGH | TFT RST（用户实测，现已不使用） |
| 38 | **无上拉，被外部拉低** | **TFT BL**（经三极管，未使能时为低；现为纯 SD CMD） |
| 39 | HIGH | **SD 总线候选** |
| 40 | HIGH | **SD 总线候选** |
| 45 | HIGH | TFT CS（用户实测，现已不使用） |
| 47 | HIGH | TFT DC（用户实测，现已不使用） |

关键结论：
- **GPIO38 无上拉且被拉低** → 符合背光经三极管控制，**不是 SD 命令线**。
- **GPIO39/40 有上拉** → 符合 SD 的 CMD/DAT 线特征。

## 4. SD 卡（根因已确认：扩展板占用 GPIO38 导致冲突）

### 4.1 官方示例原样复现

已把 `Doc/.../Sketch_04.1_SDMMC_Test` **原样**编译烧录（未改一行代码），结果与自研探测完全一致：

```
E (11) sdmmc_io: sdmmc_io_reset: unexpected return: 0x108
E (12) vfs_fat_sdmmc: sdmmc_card_init failed (0x108).
Card Mount Failed
```

**结论：不是代码问题**，官方示例在插着扩展板时同样失败。

工程位于 `hwtest/sdexample/`。

### 4.2 关键线索：0x108 与 0x107 的区别

| 引脚组合 | 错误码 | 含义 |
|---|---|---|
| CLK39 / **CMD38** / D0 40（文档值） | `0x108` INVALID_RESPONSE | **总线上有响应，但内容无效** |
| CLK40 / **CMD38** / D0 39 | `0x108` INVALID_RESPONSE | 同上 |
| CMD=39 或 CMD=40 的其他组合 | `0x107` TIMEOUT | 完全无响应 |

**规律**：只要 CMD 是 GPIO38 就得 `0x108`（有东西在应答），换成 39/40 就变成 `0x107`（彻底没应答）。

这说明 38/39/40 **确实连着 SD 卡座**，问题在电气层面而非引脚选错。

### 4.3 电气实测（阶段 8，已修正测量方法）

| GPIO | 内部下拉时 | 内部上拉时 | 判定 |
|---|---|---|---|
| **38** | 0 | **0** | **被外部电路拉低** |
| 39 | 1 | 1 | 有外部上拉 |
| 40 | 1 | 1 | 有外部上拉 |
| 41 | 0 | 1 | 空闲 |
| 42 | 0 | 1 | 空闲 |
| 47 | 1 | 1 | 外部上拉（TFT DC） |

### 4.4 **最终验证：取下扩展板后 SD 完全正常**

取下扩展板，仅保留核心板，重跑**未修改的官方示例**，结果：

```

SD_MMC Card Size: 30436MB
Total space: 30416MB
Used space: 1MB

1048576 bytes read    for 601 ms   → 约 1.67 MB/s
1048576 bytes written for 941 ms   → 约 1.07 MB/s

Listing / : System Volume Information, main.py, test.txt, foo.txt
创建/删除目录、写/追加/读/删/重命名 全部 OK
```

**根因确认无疑**：扩展板是唯一原因。取下后，`Doc` 的原始引脚 **CLK39 / CMD38 / D0 40 完全正确**，这张 32GB SDHC 卡一直工作正常。

### 4.5 根因机理

GPIO38 被两件事同时占用：

1. 扩展板 TFT 背光控制（经三极管，未使能时把线拉低）
2. 核心板 SD 卡 CMD 线（`Doc` 明确 `SD_MMC_CMD 38`）

SD 协议要求 CMD 线空闲时被上拉为高电平，靠开漏拉低通信。背光电路的下拉把这条线压住，卡无法正常应答 → `0x108`。

**这与用户实测"TFT BL = GPIO 38"完全吻合**，也解释了 `Doc` 中看似矛盾的两处记载。

### 4.6 解决方向与具体引脚

**关键判断：改 BL，不改 SD。**

| 改哪个 | 难度 | 说明 |
|---|---|---|
| **改 BL（推荐）** | **低** | 只是一根背光控制线。软件驱动可完全自定义，改完屏幕与 SD 都正常 |
| 改 SD CMD | 高 | SDMMC 外设对引脚有约束，且 CMD 是高速双向信号，飞线易受干扰 |

SD 的 CMD 线是高速双向信号，飞线会引入信号完整性问题；而 BL 只是低频开关/PWM 信号，飞线几乎无风险。

#### 目标引脚：GPIO42（首选）或 GPIO41

| 引脚 | 实测状态 | 可用性 |
|---|---|---|
| **GPIO42** | 下拉读 0、上拉读 1 → **真正空闲** | ✅ **首选** |
| GPIO41 | 同 GPIO42，空闲 | ✅ 备选 |
| GPIO1 / GPIO2 | 未探测，可能被扩展板其他器件占用 | ⚠️ 次选 |
| GPIO14 | 相机未使用，但需确认扩展板是否占用 | ⚠️ 次选 |
| GPIO45 | VDD_SPI strapping，**禁止** | ❌ |
| GPIO46 | 预留按键，已占用 | ❌ |
| GPIO19/20/21 | TFT SDA/SCL/RST，已占用 | ❌ |
| GPIO47 | TFT DC，已占用 | ❌ |

**推荐 GPIO42**：实测确认悬空、无外部上拉下拉，且不是 strapping 脚，用作 PWM 调光没有启动时序风险。

#### 硬件改动步骤

1. **断开**扩展板上 TFT 座第 8 脚（BL）与核心板 GPIO38 的连接。
   - 找到扩展板上从 TFT 座 BL 脚出发、通往排针的那根走线。
   - 靠近排针处割断该走线，或挑开焊盘上的连接。
2. **飞线**：把 TFT 座 BL 脚接到核心板 **GPIO42**。
   - 线尽量短（<10 cm），BL 是低频信号，对线材要求不高。
   - 焊接后先用万用表确认：BL 与 38 已断开、BL 与 42 已导通、42 与地/电源无短路。
3. **不要碰 GPIO38 到 SD 卡槽的连接**，原厂走线保持原样。
4. 上电前再复测一次，确认 38 与 42 之间无短路。

#### 改完后软件侧要做的

```c
#define TFT_BL  42   // 原为 38
```

同时 SD 恢复原厂定义，两个功能即可并存：

```c
#define SD_MMC_CLK 39
#define SD_MMC_CMD 38
#define SD_MMC_D0  40
```

#### 验证顺序

1. 先只测 SD：插回扩展板，烧官方 SD 示例，确认能挂载。
2. 再测屏幕：确认 BL 受 GPIO42 控制，能亮能灭、能调光。
3. 最后测并行：SD 录像同时屏幕刷新，确认互不干扰。

#### 如果不想焊接（方案 B）

把 BL 直接接 3.3V（常亮），空出 GPIO38 给 SD。

- 优点：无需精细焊接，只需把 BL 从原走线断开后接 VCC。
- 代价：**失去调光与自动熄屏能力**，屏幕始终点亮，功耗略增（背光通常 20～40 mA）。
- 对 USB 常供电的监控设备，这点功耗完全可接受。

**若你只是想让项目尽快跑起来，方案 B 更省事；若希望保留调光和省电熄屏，选方案 C 接 GPIO42。**

### 4.7 **改造已完成并验证通过**（2026-11-11）

BL 已飞线至 GPIO42，实测结果：

**引脚状态变化（决定性证据）**

| GPIO | 改造前 | 改造后 | 说明 |
|---|---|---|---|
| **38** | 下拉=0、上拉=0（被拉低） | **下拉=1、上拉=1（外部上拉）** | 背光已脱离，SD CMD 恢复空闲高电平 |
| **42** | 下拉=0、上拉=1（空闲） | **下拉=0、上拉=0（被拉低）** | 现为背光三极管控制，特征吻合 |
| 39/40 | 上拉正常 | 上拉正常 | SD 数据线未受影响 |

**SD 恢复（插着扩展板）**

```
官方示例原样运行：
SD_MMC Card Type : SDHC
SD_MMC Card Size : 30436MB
目录/文件读写删改 全部 OK
```

**相机 + SD + 背光并行测试**（10 秒，背光持续翻转 100+ 次）

```
camera: OK
SD: OK, 30436 MB
Frames captured : 84 in 10076 ms   → 8.3 fps
Bytes written   : 1189209 bytes (13.8 KB/帧)
Write rate      : 115 KB/s
File on SD      : 1189209 bytes (match=YES)
无一次短写
```

这是最关键的验证：**若 BL 仍与 SD 共用引脚，背光翻转会破坏 CMD 线导致写入失败。零错误即证明两者已彻底分离。**

**结论：GPIO38 冲突已解决，屏幕与 SD 可同时工作。**

### 4.7 实测写入速度对录像的影响

- SD 顺序写入约 **1.07 MB/s**（官方 `testFileIO`，512B 循环写）。
- 该速度低于 ESP32 通常能达到的水平，部分原因是测试用 512 字节小块 + `FILE_WRITE` 反复调用，**未做缓冲优化**。
- 按 VGA JPEG 约 12.5 KB/帧、10 fps 计，录像码率需求约 **125 KB/s**，当前速度**绰绰有余**。
- 即使复杂场景涨到 40 KB/帧，也仅需 400 KB/s，仍在能力范围内。
- 正式工程应加大写入块（4～16 KB）并使用 `write()` 批量写，可显著提高吞吐。

驱动能力测试（`INPUT_OUTPUT` 模式）确认 **38/39/40 都能正常双向驱动**，并非卡死。

## 5. 对规划的影响

### 5.1 JPEG 大小修正（重要）

实测单帧约 **12.5～13.8 KB**（简单场景到含细节场景），原估算 35 KB。

10 秒录像（约 100 帧）：

| 估算依据 | 单段大小 |
|---|---|
| 原估算 35 KB/帧 | 约 3.5 MB |
| **实测 12.5～13.8 KB/帧** | **约 1.25～1.4 MB** |

32 GB 卡（可用约 30 GB）可存：

| 每天事件数 | 每天占用 | 可存天数 |
|---|---|---|
| 100 | 约 130 MB | 约 230 天 |
| 300 | 约 400 MB | 约 77 天 |
| 1000 | 约 1.3 GB | 约 23 天 |

容量比原规划宽裕约 3 倍。实测并行写入测试中，剩余 30414 MB 可存约 **25513 段** 10 秒录像。

### 5.2 带宽修正

远程推流码率相应下降：

| 档位 | 按 35 KB 估算 | 按 12.5 KB 实测 |
|---|---|---|
| VGA / 10 fps | ~2.8 Mbps | **~1.0 Mbps** |
| VGA / 5 fps | ~1.4 Mbps | ~0.5 Mbps |
| QVGA / 8 fps | ~0.45 Mbps | ~0.16 Mbps |

**结论：轻量服务器带宽约束大幅缓解**，VGA/10fps 远程可能可行（约 1 Mbps），不再必须强制降档到 QVGA。仍需实测真实场景（复杂画面 JPEG 会变大）。

### 5.4 TFT 驱动实测要点（ST7789 / GMT020）

> ⛔ **本节为历史记录：相关驱动代码（`src/display/`、`src/ui/font5x7.*`、
> `src/storage/avi_reader.h`）已随 M8 全部删除，`TFT_eSPI` 依赖也已移除。**
> 保留此处是为了记录当时的排障结论，避免以后再次踩同样的坑。

M5 阶段踩过的三个坑，均已在当时的代码中修正：

| 问题 | 错误现象 | 根因与修正 |
|---|---|---|
| 栈溢出 | `Stack canary watchpoint triggered (display)`，崩溃地址 `0x400570e5` | `JPEGDEC jpeg;` 声明在栈上，该类内嵌约 16 KB 缓冲（`usHuffAC` 8K + `usUnalignedPixels` 4K + `ucFileBuf` 2K + `ucHuffDC` 2K）。→ 改为堆分配 `new JPEGDEC()` |
| 背光不亮 | 屏幕全黑 | 背光误用 `LEDC_CHANNEL_0/TIMER_0`，而 **esp32-camera 正是用该通道驱动 OV2640 XCLK**（见 `esp32-camera/target/xclk.c`），重新绑定会抢走摄像头时钟。→ 改用 `CHANNEL_2/TIMER_2` |
| 雪花/无内容 | 屏幕显示随机噪声 | `COLMOD`、`MADCTL` 等 ST7789 参数是**单字节**，却被当成 16 位发送（多一个前导 `0x00`），整串寄存器错位。→ 新增 `spiWriteData8()`，仅在 CASET/RASET 用 16 位 |

**性能实测（VGA 640×480，8 MB PSRAM，历史数据）**：

| 场景 | 实测帧率 | 空闲堆 |
|---|---|---|
| 仅本地显示 | 约 5.3 fps | 197 KB |
| 显示 + 网页直播 | 约 11.6 fps | 184 KB |
| 直播结束后 | 4.8～6.1 fps | — |

显示任务当时运行在 core 1、优先级仅高于空闲任务，录像与推流不受阻塞。

## 6. 已知的固件/工具链注意点

- 仅烧录 `firmware.bin` 到 `0x10000` 会触发 `SHA-256 comparison failed`，虽仍能启动，但**正常流程应烧完整镜像**（bootloader + partition table + app）。
- 默认分区表无 core dump 分区，启动日志会出现 `No core dump partition found!`，属正常提示，正式工程需补上 coredump 分区。
- **GPIO26～32 是 SPI Flash 引脚，HP 与 poking 会导致看门狗复位**，扫描时必须排除。
- GPIO33～37 为 Octal PSRAM 占用，同样不可触碰。

## 9. 测量方法上的教训

记录一次实际踩坑，避免重复：

**错误做法**：`gpio_set_direction(pin, GPIO_MODE_OUTPUT)` 后调用 `gpio_get_level()` 读回，**结果恒为 0**，因为纯 OUTPUT 模式关闭了输入缓冲。

**正确做法**：
- 要判断外部电路状态 → 用 `GPIO_MODE_INPUT` + 内部上/下拉，观察电平是否被外部拉走
- 要测试驱动能力 → 用 `GPIO_MODE_INPUT_OUTPUT`，读回才有效

这个 bug 导致阶段 7 误报"38/39/40 全部 STUCK LOW"，与阶段 3 的"39/40 有上拉"自相矛盾。**当两次测量结论冲突时，应优先怀疑测量方法。**
